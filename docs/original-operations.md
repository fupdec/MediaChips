# Managing originals

**Manage originals** is available in the media editor, in the selection toolbar, and in the NAS and Google Drive folder browsers. The browsers also support creating a folder and uploading into an empty folder. Operations are presented in this order: download, transfer between sources, rename, create folder / upload, move, delete.

The media editor's existing path rename and the existing bulk move dialog use the same durable server operations. Removing media from the library uses the existing card/Trash flow. **Delete original** requires an explicit confirmation and deletes only the source bytes; it keeps the card, user title, rating, favorite, views, dates, chips, values, chapters, playlists and generated assets. Rename/move likewise updates the existing card rather than importing a replacement. Local folder chips inherited at read time are materialized before changing the path. NAS locations and matching offline copies follow the renamed original. Drive keeps its `gdrive://<id>` identity.

## Execution and recovery

A library-local SQLite journal (`originalOperationJobs`, migration 0035) records each item, progress, source identity and publication/link/unlink checkpoints. A server queue runs one job at a time. Items within a batch run in submission order; the first failure pauses the rest of that batch. Retrying skips completed/skipped items. A later move/delete in the same batch can follow an earlier successful rename of that card. Unrelated queued work cannot silently follow a card relinked to a different original.

Progress shows transferred bytes, total bytes and per-item state. A browser refresh or dialog close does not cancel server work. An interrupted running job is offered for explicit retry after restart. Queued jobs run when the server is available. Source configuration and active library changes invalidate the in-flight job. Reconciliation/offline jobs share connection locks with mutations, so a catalog scan cannot publish an inventory taken halfway through a move.

Conflicts support stopping, skipping and keeping both under an unused numbered name. Existing bytes are never intentionally replaced. Local publication uses an exclusive file creation and hard link, WebDAV uses `Overwrite: F` / conditional PUT, and SFTP uses exclusive creation and standard rename. FTP checks destinations immediately before STOR/RNTO; FTP has no portable conditional rename primitive, so external writers should not concurrently change those same paths. Drive allows duplicate names natively; name checks cover every folder page and recheck after publication. A concurrent duplicate leaves a failed job with its reserved object ID for review/retry, rather than overwriting another file.

Same-volume local rename/move uses a hard link, database update, then unlink, without a second full-sized copy. Filesystems that do not support it and cross-volume moves use a verified temporary copy. Downloads and uploads publish from a unique `.mediachips-<item-id>.part` only after checking byte counts and source version. Copy recovery verifies the saved checksum before linking the card or unlinking its old path. NAS moves also verify full content before/after the move, including recovery after a lost MOVE reply. If an ambiguous remote result cannot be verified, the job stops for inspection instead of guessing which file is the original. Retrying an interrupted transfer continues from its verified byte checkpoint when the source supports ranged reads and the destination supports positional writes. Completed items are never repeated.

Browser uploads stream into a private per-library server spool beside the offline-storage directory (`<library-hash>-uploads`), with a free-space check. Files waiting for other batch uploads are retained across restart. A fully committed spool file is recoverable even if its acknowledgment was lost. Incomplete uploads require selecting the file again. Spools are removed after completion/skip. Download destinations are absolute paths **on the MediaChips server**, which may differ from the browser's computer. NAS destinations are paths relative to its configured root. Parents must exist; a batch may create a parent before uploading/moving into it. Moves stay within one connection; **Transfer between sources** handles copying between connections in one managed operation.

## Continuing interrupted files

The journal saves the source version, total size and SHA-256 hashes of consecutive 8 MiB staging blocks. After a retry or server restart, the service checks the source version and size, reads and validates the retained destination blocks, discards any unconfirmed tail, and requests only the remaining source bytes. A source version change stops the job with `source_changed`; corrupt staging bytes stop it with `size_mismatch`. Progress is restored from the verified offset, rather than trusting bytes read ahead of the writer. Publication and optional source removal still require complete content verification.

Local destinations (including the private transfer spool) and SFTP staging files support positional writes. NAS/Drive originals can continue into local staging using their ranged readers. FTP/FTPS and WebDAV destinations currently restart the staging upload because their adapters do not expose a portable safe positional write. A source that ignores Range also falls back to a fresh staging copy. Unfinished browser-to-server uploads still require selecting the file again; a completely received browser spool survives restart as before.

Drive uploads journal their resumable session before sending bytes. A retry queries Drive for the confirmed offset and opens the checked spool at that position. Expired sessions restart under the same reserved file ID; completed sessions and lost final responses are recovered without creating another object. Before continuing, the spool's version, size and checksum must still match. Session URLs remain private to the SQLite journal and are omitted from all job API responses. This follows the official [Drive upload recovery protocol](https://developers.google.com/workspace/drive/api/guides/manage-uploads#resume-upload).

## Transfer between sources

Select one or more cards, choose **Transfer between sources**, then select local server storage, a configured NAS connection, or a connected writable Google Drive as the destination. Enter the destination folder using that source's path format. A batch may contain originals from different connections. Read-only originals can be copied.

The default mode is **Keep the source**. The server reads and hashes the complete original, saves a checked temporary spool, publishes through the existing upload machinery, then independently reads the destination and compares its full SHA-256 and size. This verification always uses SHA-256, regardless of the library's duplicate-comparison setting. After rechecking the source, the server checks the destination version and size again immediately before linking; a change stops the operation before updating the card or registering copies. Only a verified destination is added to the existing card's locations and verified copies; the original path stays unchanged. Titles, ratings, favorites, views, dates, chips, values, chapters, playlists and generated assets stay with the same card. No reimport or replacement card is created.

**Delete the source after verification** is a separately selected mode with explicit confirmation. The card switches to the verified destination, inherited folder chips are materialized, and the link and recovery checkpoint commit together. Immediately before deletion, the service verifies both contents again and checks the source version. Only the removed location is marked unavailable. If verification, linking or deletion fails, the batch stops and the saved job can be retried. A retry after linking checks the destination again before attempting source deletion; an already deleted source is reconciled without uploading again.

Transfers use a private server spool, so free server disk space for one complete original is required even for NAS → cloud. Spools and nested upload checkpoints survive restart. Drive publication retains its reserved file ID, allowing recovery after a lost upload response without a duplicate object. Closing the dialog does not cancel the transfer. Fail/skip/keep-both conflict policies apply at the destination; skipping does not add a location or delete the source. Temporary spools are removed after completion or skip. Native Google Workspace documents are rejected.

## Google Drive

Writing previously imported files requires reconnecting in Settings → Sources and approving the `https://www.googleapis.com/auth/drive` OAuth scope. Existing read-only authorizations continue reading/downloading and cannot write. Each destructive request checks the file's account capabilities and an observed ETag when provided. Folder destinations use Drive folder IDs (`root` means My Drive).

Creation reserves a Drive file ID and journals it before creating a folder or starting a resumable binary upload. Uploads retain that ID, check the provider's MD5 checksum against the spool and rename the verified staging object. A lost final response is recovered by looking up the reserved ID; no duplicate upload is created. Rename/move uses `files.update`, preserving the source ID and card metadata. Deleting an original uses `files.delete`, permanently removing the Drive file while retaining its MediaChips card. Native Google Workspace documents are not binary originals and are rejected.

API behavior follows the official [Drive upload guide](https://developers.google.com/workspace/drive/api/guides/manage-uploads), [pre-generated file IDs](https://developers.google.com/workspace/drive/api/guides/create-file#use_a_pre-generated_id_to_upload_files), and [update API](https://developers.google.com/workspace/drive/api/reference/rest/v3/files/update).

## API and checks

The authenticated API is under `/api/original-operations`: `GET /destinations`, `GET /media/:id`, `GET/POST /jobs`, `GET /jobs/:id`, `POST /jobs/:id/retry`, `POST /jobs/:id/cancel`, and streaming `PUT /jobs/:id/uploads/:itemId`. Batch validation is in `shared/originalOperations.ts`. A transfer submits one item with `kind: 'transfer'`, `mediaId`, `target` and `conflict`. Source removal additionally requires both `removeSource: true` and `confirmDelete: true`. Responses expose paths and stable error codes, never connection secrets or provider error bodies.

Regression coverage includes real temporary files and SQLite, failure checkpoints before/after card updates, lost NAS/Drive replies, conflict policies, stopping downstream deletion after failure, raw HTTP uploads, local SFTP/FTP/HTTPS protocol fixtures, mocked Google API authorization/capabilities/resumable requests, and a browser scenario for progress, conflict retry, upload and reopening recovery history. Mock Drive requests do not establish interoperability with a live Google account.
