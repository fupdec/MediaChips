# Безопасность обновления библиотеки с удалёнными источниками

Проверка: 21 октября 2026 года. Пользовательские библиотеки и оригиналы не открывались и не изменялись. Все базы, файлы и хранилища учётных данных в тестах временные.

## Исходная версия и границы подтверждения

В репозитории последний локальный тег — `v1.12.0`. Его Drizzle-журнал заканчивается `0030_tag_category_parent_indexes`; в рабочем дереве — `0041_copy_discovery_automation`. При первоначальной проверке `package.json` рабочего дерева также имел версию `1.12.0`; подготовленный 24 октября кандидат имеет версию `1.13.0`. Номер приложения сам по себе не определяет совместимость схемы.

GitHub API и страница latest недоступны из среды проверки. Поэтому статус именно последнего **публичного** релиза не подтверждён. База для регрессии воспроизводится из SQL и column repairs локального тега, а не из текущей схемы с удалёнными записями журнала. Фикстура: `api/db/testUtils/fixtures/v1.12.0.sql`. Это синтетическая база исторической схемы с пользовательскими данными, не реальная библиотека, созданная установленным старым приложением. Проверка другого публичного тега требует отдельного повторения.

## Найденные и исправленные дефекты

- Архивация живого `db.sqlite` могла пропускать изменения в WAL. Теперь используется SQLite online backup; ZIP публикуется после завершения записи через временный `.partial`, имена уникальны.
- Восстановление удаляло текущую базу и assets до проверки архива. Теперь ZIP распаковывается в staging, проверяются состав и SQLite integrity, затем прежние файлы сохраняются до успешного reload. Ошибка открытия/миграции вызывает возврат прежней базы и assets. Неожиданные файлы вне `db.sqlite`, `media`, `meta` отклоняются.
- Legacy backfill мог заменить пользовательский заголовок, когда отсутствовали `basename`/расширение. Теперь заполняются только пустые поля, удалённые URI не обрабатываются как файловые пути, extensionless-файлы не переписываются при каждом запуске.
- Текущий migrator теперь отказывает до repairs, если timestamp последней миграции больше поддерживаемого. Это защита от будущих схем с более новым журналом, не универсальный детектор произвольных ручных изменений схемы.

## Подтверждённый порядок обновления

1. В старой версии остановить импорт, обработку, перемещения и фоновые записи; закрыть приложение. Сделать отдельную полную копию каталога библиотеки и сохранить старый установщик. Закрытая библиотека важна: старый механизм ZIP мог не учитывать WAL. Не копировать только `db.sqlite` работающего приложения.
2. Работать сначала с копией библиотеки. Открыть её новой версией; дождаться завершения миграций. Проверить карточки, пользовательские названия, теги, рейтинги, метки и плейлисты. Закрыть и повторно открыть.
3. Для переноса на другой компьютер скопировать библиотеку при закрытом приложении либо восстановить новый ZIP. Оригиналы по локальным абсолютным путям сами не переносятся: скопировать их отдельно и использовать relink корня. При наличии полного SHA-256 relink проверяет идентичность; без достаточного доказательства требуется явное подтверждение оригинала.
4. Повторно ввести NAS credentials или настроить OAuth на **существующем** подключении. Не создавать заменяющее подключение с новым ID. Vault намеренно вне библиотеки и ZIP; секреты не должны переноситься с общим архивом. Для legacy Google Drive повторно подключить legacy Drive.
5. Перед автоматическим поиском копий включить полную проверку SHA-256, если требуется доказательство неизменности содержимого и таймкодов. Режим по умолчанию oshash сравнивает размер и выборки; совпадающие края не доказывают совпадение середины файла.
6. Создать копию новым механизмом и проверить её восстановление в отдельную библиотеку. После успешной проверки можно обновлять рабочую библиотеку; сохранить предобновлённую копию отдельно.

## Границы отката и ограничения

- **Безопасный откат:** закрыть новую версию, сохранить её библиотеку отдельно, запустить старую версию только с полной копией, сделанной **до обновления**. Изменения после обновления в эту копию не попадут. Перенос их назад автоматически не предусмотрен.
- Открытие новой базы старым бинарником **не поддерживается**. В коде тега `v1.12.0` нет проверки будущей схемы; старый migrator ориентируется на последний timestamp, а старые repairs/legacy upgrades могут продолжить запись. Успешное открытие SQLite не доказывает совместимость. Не удалять журнал миграций и новые таблицы для «отката».
- Новый schema guard не защищает старый установленный бинарник и не заменяет предобновлённую копию. Down migrations отсутствуют.
- NAS disconnect и cloud logout сохраняют connection metadata и mediaLocations. Физическое удаление строк подключения вручную не является поддерживаемым сценарием: без исходных идентификаторов нельзя гарантировать восстановление связи. Недоступный источник не означает удалённую карточку.
- ZIP содержит базу и `media`/`meta`; внешние оригиналы, NAS/облако, vault, offline/transcode caches в него не входят. Резервирование assets не является общим атомарным снимком с SQLite: на время копирования остановить изменяющие assets задачи.
- Восстановление использует последовательные переименования нескольких файлов, а не транзакцию файловой системы. При остановке процесса/потере питания может остаться `.restore-previous-*`; закрыть приложение и сохранить этот каталог до ручного восстановления. Автоматический recovery после power loss не реализован. Параллельные restore/import блокируются механизмом эксклюзивного восстановления, описанным ниже.
- Legacy LowDB-архивы идут через отдельный старый importer; новый механизм rollback предназначен для SQLite ZIP. Приёмка LowDB в этот результат не входит.
- HTTP-сценарии NAS/copies/discovery нельзя подтвердить в этой среде: `listen(127.0.0.1)` не создаёт сервер. Живые провайдеры и установленный старый/новый Electron здесь не проверялись.

## Проверки

Использован Node 22.22.0; системный Node 14 несовместим с текущим Vitest/better-sqlite3. Native binding пересобран для Node 22.

- 13 целевых файлов (миграции/repair, upgrade, backup, relink, history, copy automation, NAS recovery, cloud accounts): 83 теста прошли.
- Copies/discovery: 36 тестов прошли, два HTTP-теста исключены запуском с `-t '^(?!.*HTTP)'`. Всего 119 целевых проверок прошли.
- Полный первоначальный запуск: HTTP-тесты заблокированы ограничением локальных портов; они не считаются пройденными.
- API strict typecheck: в существующем `cloudAccounts/accounts.test.ts` две ошибки `Object is of type unknown` (69, 94); ошибки в изменениях этой задачи исправлены. Полный typecheck до устранения этих ошибок не зелёный.

Вывод: путь обновления **с воспроизведённой схемы локального v1.12.0** подтверждён целевыми регрессиями при указанных условиях. Универсальное разрешение обновления с последнего публичного релиза требует подтверждения публичного тега и прогона установленного приложения на копии реальной библиотеки этого релиза.

## Блокировка на время восстановления

Сервер устанавливает эксклюзивную блокировку до проверки архива. Новые API-операции и повторное восстановление получают HTTP 409 с кодом `library_restoring`; ping/config остаются доступны. Периодические работники пропускают запуск, файловые наблюдатели закрываются. Уже начатые операции, включая очереди обработки, копирование/загрузку оригиналов, каталогизацию, offline-загрузки и WebSocket-перемещения, получают время для завершения. Их вложенные задачи могут закончить работу; закрытие HTTP-клиента не снимает блокировку с отдельно отслеживаемых фоновых задач.

Ожидание ограничено 30 секундами. При превышении сервер возвращает HTTP 409 `library_busy`, не открывая архив и не заменяя библиотеку; нужно дождаться завершения длинных задач и повторить восстановление. Блокировка держится до конца восстановления, включая откат при ошибке. Затем периодические работники могут запускаться снова; после успешного восстановления интерфейс перезагружает данные и подключает наблюдатели заново. SQLite и legacy LowDB-восстановление используют одну блокировку. При замене меняется поколение операций: запоздавшие обращения к общим прокси БД от отключившихся клиентов отклоняются и после снятия блокировки.

Регрессии проверяют ожидание фоновой записи перед заменой файлов, отказ повторному восстановлению, блокировку API и периодических работников при закрытой БД, вложенные очереди, тайм-аут без замены файлов и снятие блокировки после отката.
