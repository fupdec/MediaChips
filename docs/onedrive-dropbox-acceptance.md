# Приёмка OneDrive / Dropbox — 2026-10-21

Решение: **оба провайдера остаются beta**. Живая приёмка не выполнена. Пользовательские библиотеки, облачные оригиналы и существующие credentials не менялись. Публикация не выполнялась.

## Результаты

47 тестов прошли в 6 файлах: accounts, providers, mediaMetadata, metadataBackfill, importAcceptance и cloudOAuthCallback. HTTP acceptance: 21 тест не выполнил сценарии из-за `listen EPERM 127.0.0.1`. Браузерный E2E не запускался: тот же listener недоступен. Существующий `e2e/cloud-accounts.spec.ts` подменяет API и не доказывает live-приёмку.

## Исправления

- Dropbox download и thumbnail явно используют `Content-Type: application/octet-stream`. Воспроизведено, что Axios иначе добавляет к пустому POST `application/x-www-form-urlencoded`; подмена CloudRequest скрывала этот дефект. Добавлена регрессия для обоих endpoints, пустого тела и ASCII-экранирования Unicode.
- Acceptance fixture использует полный callback `/api/cloud-accounts/oauth/callback`, согласованный со схемой и проверкой порта.
- Ошибка listener корректно отклоняет setup promise вместо вторичной ошибки чтения `null.port`.
- Исправлена типизация порта legacy Drive, блокировавшая backend compilation.
- Добавлены тесты импорта трёх типов медиа и lifecycle обоих провайдеров с отдельными временными БД/vault.

## Воспроизводимый живой стенд

Требуется Node 22.22+ и машина с разрешённым loopback listener. Из корня репозитория:

```sh
npm run build:app
node scripts/ensure-sqlite-tests.mjs
node scripts/cloud-acceptance-server.mjs /tmp/mc-cloud-acceptance-live
```

Открыть `http://127.0.0.1:12331`. Стенд создаёт отдельные config, app_storage и vault. Он отказывается использовать существующий config без своей метки. Для перезапуска остановить процесс и повторить ту же команду с той же директорией. Не запускать обычный Playwright config против пользовательского сервера: он допускает reuseExistingServer.

В каждом OAuth-приложении зарегистрировать **точно** `http://127.0.0.1:12331/api/cloud-accounts/oauth/callback` (и допустимый платформенный тип). OneDrive: Files.Read, offline_access, нужная аудитория личных/рабочих аккаунтов. Dropbox: files.metadata.read, files.content.read, offline flow, доступ к тестовой папке. Указать Client ID/App key и необходимые secret только в интерфейсе тестового профиля.

Использовать по два тестовых аккаунта каждого провайдера. В каждом подготовить отдельную папку `Приёмка 文件 🎬`, вложенную папку, видео MP4 H.264/AAC, MP3 и PNG, а также более 200 небольших файлов для реальной второй страницы. Загружать только специально созданные тестовые файлы; не перемещать и не редактировать пользовательские оригиналы.

Для каждого провайдера:

1. Войти в A и B через настоящий browser consent. Проверить успешный статус, отказ и отмену, повторный вход.
2. Открыть вложенную Unicode-папку, пройти все страницы; сверить уникальные ID и количество.
3. Импортировать три медиа; записать ID. Изменить название, рейтинг, чипсы, маркеры и позицию просмотра. Повторить импорт; сверить ID, количество и все поля.
4. Открыть изображение, проиграть аудио/видео, перемотать вперёд/назад; проверить HTTP 206 и Content-Range. Сохранить старый playback URL локально, не публиковать его.
5. Перезапустить стенд с тем же профилем. Проверить подключения, карточки и воспроизведение. Дождаться реального истечения access token, затем запросить список и воспроизведение: проверить реальный refresh без нового consent. Не выдавать искусственный токен или смену часов за эту проверку.
6. Выйти из A: запросить старый playback URL и callback, убедиться в отказе. Проверить работоспособность B. Заново подключить A и повторить импорт: прежние ID/пользовательские поля сохраняются, старый URL остаётся недействителен.
7. Повторить, поменяв A/B ролями. Проверить, что одноимённые файлы аккаунтов не смешиваются. Зафиксировать ОС, сборку, время, ID тестовых карточек, статусы запросов без токенов/секретов.

## Чего не хватает

Нужны настроенные OAuth registrations обоих провайдеров и по два доступных тестовых аккаунта с указанными файлами. Ввод секретов — локально в тестовый профиль, не в чат или репозиторий. Также требуется запуск на машине, разрешающей listener: текущая среда автоматически запрещает его. Даже после unit-тестов beta нельзя снимать без описанной живой приёмки и проверки установленной сборки.
