# Подключение облаков: подготовка публичного релиза

## Решение и граница готовности

Кнопка «Подключить» в диалоге добавления облачного аккаунта использует OAuth-клиент, настроенный администратором API MediaChips. Ключи передаются только API. Ручная форма доступна в дополнительных настройках. Существующий основной Google Drive сохраняет свой отдельный OAuth-клиент, права на операции с оригиналами и идентификаторы файлов.

## Регистрация для кнопки «Подключить»

Для размещённого API используйте один и тот же точный адрес возврата во всех трёх консолях. Подставьте публичный HTTPS-адрес самого API вместо примера: `https://mediachips.example/api/cloud-accounts/oauth/callback`. Маршрут должен быть доступен браузеру пользователя. Для локальной установки задайте loopback-адрес с фактическим портом API, который поддерживается регистрацией выбранного провайдера.

- **Google Cloud.** Включите Drive API. Настройте экран согласия и создайте OAuth-клиент типа **Web application**. Добавьте адрес в **Authorized redirect URIs**. Подключение запрашивает `https://www.googleapis.com/auth/drive.readonly`. Для режима Testing добавьте тестовых пользователей. Для публичного выпуска Google требует проверку приложения для этого restricted scope.
- **Microsoft Entra.** Зарегистрируйте приложение с поддержкой рабочих, учебных и личных аккаунтов Microsoft. Добавьте платформу **Web** и адрес возврата. В Microsoft Graph добавьте делегированное разрешение `Files.Read`. Запрос MediaChips также включает `offline_access`. Создайте client secret и сохраните его **Value**.
- **Dropbox.** Создайте приложение типа **Scoped access** с **Full Dropbox**, чтобы открывать существующие файлы пользователя. Добавьте адрес в **Redirect URIs** и включите `files.metadata.read` и `files.content.read`. Для публичного распространения оформите Production status.

Передайте переменные процессу API и перезапустите его. Провайдер появляется в быстром подключении, когда заданы оба его ключа и корректный адрес возврата.

```dotenv
MEDIA_CHIPS_CLOUD_REDIRECT_URI=https://mediachips.example/api/cloud-accounts/oauth/callback
MEDIA_CHIPS_CLOUD_GOOGLE_CLIENT_ID=
MEDIA_CHIPS_CLOUD_GOOGLE_CLIENT_SECRET=
MEDIA_CHIPS_CLOUD_ONEDRIVE_CLIENT_ID=
MEDIA_CHIPS_CLOUD_ONEDRIVE_CLIENT_SECRET=
MEDIA_CHIPS_CLOUD_DROPBOX_CLIENT_ID=
MEDIA_CHIPS_CLOUD_DROPBOX_CLIENT_SECRET=
```

Храните секреты в окружении управляемого сервера. Распространяемая настольная сборка по-прежнему требует собственного OAuth-клиента для локального API либо отдельного OAuth-брокера.

## Пользовательский сценарий текущей реализации

1. Запустить установленный MediaChips на том же компьютере, где откроется системный браузер. Для удалённого сервера loopback указывает на компьютер браузера и не подходит: требуется отдельно зарегистрированный достижимый HTTPS callback.
2. В подключениях выбрать существующий Google Drive либо добавить облачный аккаунт. При наличии серверной регистрации выбрать провайдера и нажать «Подключить». Для собственной регистрации открыть дополнительные настройки OAuth.
3. В новой форме callback берётся из `/api/cloud-accounts/configuration`, то есть с фактического порта API: обычно `http://127.0.0.1:12321/api/cloud-accounts/oauth/callback`. Старый Drive по умолчанию использует тот же фактический порт и путь `/api/drive/oauth/callback`. Адрес Vite/страницы интерфейса не используется. Сохранённый callback не переписывается молча: несовпадающий loopback-порт блокируется до открытия браузера. Исправить адрес в форме и в консоли провайдера.
4. Нажать подключение, завершить вход в системном браузере. Интерфейс опрашивает результат и автоматически обновляет список аккаунтов; вручную нажимать «Обновить» для завершения входа не нужно. При отказе, ошибке или истечении сеанса можно начать заново.
5. «Отменить вход» инвалидирует попытку, включая уже запущенный обмен кода. Поздний callback не восстановит авторизацию. Повторный вход отменяет предыдущую попытку только этого аккаунта. Отключение удаляет локальные токены; оно не отзывает разрешение у провайдера.
6. Завершённая авторизация сохраняется после перезапуска API. Незавершённый вход после перезапуска считается истёкшим, требуется начать заново. State одноразовый, действует 10 минут; PKCE S256 применяется в обоих Google flow.
7. При запросе файлов просроченный токен обновляется в API. Параллельные запросы одного поколения авторизации используют один refresh. Ответ refresh без нового refresh_token сохраняет прежний. При invalid_grant токены удаляются и требуется повторный вход. Сбой сети не удаляет действующую сохранённую авторизацию. Logout/перенастройка во время обмена не восстанавливает старые токены.

## Совместимость Google Drive

| Подключение | Callback | Права | Идентичность файлов |
| --- | --- | --- | --- |
| Старое Google Drive | `/api/drive/oauth/callback` | `drive` для операций с оригиналами; старые read-only токены продолжают чтение | `gdrive://fileId` |
| cloudAccounts Google Drive | `/api/cloud-accounts/oauth/callback` | `drive.readonly` | `gdrive://accountUUID/encodedKey` |

Это независимые подключения с разными полномочиями и идентичностями. Нельзя автоматически переносить токены или подменять старое подключение новым: сломаются ссылки/права. Настройка, повторный вход и отключение сохраняют исходные идентификаторы подключений и карточек. Новая форма объясняет read-only характер дополнительного Google аккаунта. PKCE и правила callback согласованы, разница scope сохранена намеренно.

## Хранение и сборка

cloudAccounts уже использует host-local AES-256-GCM vault; старый Drive переведён на тот же механизм. Запись шифротекста атомарная, файлы создаются с 0600, каталог с 0700. Старый приватный JSON переносится при чтении; удаляется после успешной записи. Master key лежит на том же компьютере: это защита от случайного попадания в библиотеку/бэкап, не защита от пользователя, полностью контролирующего хост.

Найден и удалён игнорируемый git файл `public/drive-oauth-tokens.json`, а также его копия в `dist`. Добавлен запрет запуска Vite и сборки при повторном появлении этого файла. Не переносить эти токены в новый vault: их нужно отозвать. Старые артефакты и PWA caches могли уже содержать их; удаление из текущего дерева не отзывает выданный Google доступ.

## Проверки и реальная приёмка

Автоматические unit/component проверки используют подменённый token endpoint: они проверяют логику приложения, а не реальный OAuth. Проверяются одноразовый state, denial, отмена до/во время обмена, restart, logout race, PKCE, invalid_grant, параллельный refresh и перенос/очистка токенов. Пройдено 84 целевых теста (8 файлов), frontend/backend typecheck и production build.

HTTP acceptance suite использует настоящий локальный HTTP listener, но подменённого провайдера. В данной среде listener запрещён (`listen` возвращает `EPERM`); эти проверки не засчитываются как пройденные. В тестовых fixture callback исправлен на фактический API origin. E2E установленной Electron-сборки и настоящий provider OAuth не выполнены.

На машине с разрешёнными loopback-портами выполнить:

- `npm exec vitest run api/services/cloudAccounts/acceptance.test.ts`.
- Установить packaged app на чистый профиль, запустить рядом dev-сервер Vite, сверить callback в обоих подключениях и URL согласия. Проверить также занятый порт: не должно быть тихого перехода на dev callback.
- Для каждого провайдера: успешное согласие → автоматический статус → список реальных файлов → перезапуск приложения → список файлов → реальное обновление истёкшего access token.
- Отказ провайдера, закрытие браузера с последующей явной отменой, повторный вход другим аккаунтом, отмена во время callback, повтор старого callback, перезапуск при незавершённом входе, потеря сети и её восстановление.
- Отозвать доступ в настройках аккаунта провайдера, дождаться refresh: UI должен потребовать повторный вход; карточки и их идентификаторы сохраняются.
- Проверить отсутствие токенов/секретов в dist, asar, devtools responses и логах. Проверить обновление существующей установки с приватным legacy tokens.json.

## Точные внешние действия / блокеры

1. Немедленно отозвать Google grant, которому принадлежали токены из public/dist, через настройки доступа Google Account. Очистить ранее собранные/разданные артефакты и их caches; при подозрении на утечку client secret перевыпустить его в Cloud Console. Не использовать найденные токены для приёмки.
2. Google Cloud Console: выбрать проект MediaChips, включить Drive API, оформить OAuth consent/branding, support contact, privacy policy, verified domains и аудиторию. Определить production OAuth client type и flow. Зарегистрировать оба точных callback для ручного Web client. Для отдельного Desktop flow использовать Desktop client и проверить требования обмена на реальных credentials. Секрет хранить только на стороне владельца API/управляемого broker, не распространять в сборке.
3. Согласовать необходимые Drive scopes: legacy `drive` и новые `drive.readonly`; пройти требуемую Google проверку этих scopes и выяснить применимость security assessment к выбранной инфраструктуре. Перевести consent из Testing в Production после одобрения; тестовые пользователи не подтверждают массовую доступность.
4. Microsoft Entra: зарегистрировать приложение с нужной аудиторией аккаунтов, `Files.Read` и `offline_access`, точным redirect и допустимым типом платформы; разрешить public-client PKCE flow, если он выбран, без confidential secret в клиенте. Dropbox App Console: зарегистрировать app, доступ к нужным файлам, `files.metadata.read`, `files.content.read`, точный redirect и offline access; получить production approval при необходимости.
5. Предоставить реальные client registrations/тестовые аккаунты и выполнить вышеуказанную приёмку на Windows/macOS/Linux. Успешный invalid-refresh-token preflight старого Drive подтверждает лишь ответ token endpoint, а не валидность redirect, scope, consent или реальный вход.
6. Для обещания «просто войти без собственных ключей» реализовать и проверить publisher flow после выбора реальной регистрации и инфраструктуры. Текущую ручную форму нельзя выдавать за завершённый массовый пользовательский сценарий.

Официальные источники: [Google Desktop OAuth/PKCE](https://developers.google.com/identity/protocols/oauth2/native-app), [Google Web server OAuth](https://developers.google.com/identity/protocols/oauth2/web-server), [Drive scopes](https://developers.google.com/workspace/drive/api/guides/api-specific-auth).
