# Подключение облаков: подготовка публичного релиза

## Решение и граница готовности

Кнопка «Подключить» в диалоге добавления облачного аккаунта использует OAuth-клиент, настроенный администратором API MediaChips. Ключи передаются только API. Ручная форма доступна в дополнительных настройках. Существующий основной Google Drive сохраняет свой отдельный OAuth-клиент, права на операции с оригиналами и идентификаторы файлов.

## Регистрация

Вход полностью ведёт серверная часть: интерфейс (браузер или Electron) только открывает ссылку и опрашивает статус. Публичный адрес и сторонний брокер не нужны. Для каждого провайдера требуется собственный OAuth-клиент; издательского входа «без своих ключей» в 2.0.0 нет.

### Адреса возврата

| Подключение | Адрес возврата |
| --- | --- |
| Основной Google Drive и дополнительные Google-аккаунты с общим клиентом | `/api/drive/oauth/callback` |
| Дополнительные аккаунты со своим клиентом, OneDrive, Dropbox | `/api/cloud-accounts/oauth/callback` |

Какой бы из двух адресов ни принял ответ, завершить вход можно для любого провайдера: оба маршрута (и оба маршрута вставки ссылки) передают `state` одному диспетчеру, который находит владельца попытки. Регистрировать у провайдера нужно тот адрес, который клиент отправляет в запросе согласия.

- **Локальная установка и NAS.** Адрес строится автоматически: `http://127.0.0.1:<порт API>/api/.../oauth/callback` (обычно порт `12321`). Адрес Vite и страницы интерфейса не используется. Сохранённый адрес не переписывается молча: loopback с другим портом блокируется ошибкой `redirect_uri_mismatch` до открытия браузера. Исправьте адрес в форме и в консоли провайдера.
- **Публичный адрес за HTTPS.** Укажите его вместо loopback, например `https://mediachips.example/api/cloud-accounts/oauth/callback`. Маршрут должен быть доступен браузеру пользователя. Любой не-loopback адрес считается достижимым.

### Провайдеры

- **Google Cloud.** Включите Drive API, настройте экран согласия и создайте OAuth-клиент. Тип **Desktop app** принимает любой loopback-порт без регистрации адреса. Для типа **Web application** добавьте точный адрес в **Authorized redirect URIs**. Основной Drive запрашивает `https://www.googleapis.com/auth/drive`, дополнительные аккаунты — `https://www.googleapis.com/auth/drive.readonly`. В режиме Testing добавьте тестовых пользователей; для публичного выпуска Google требует проверку приложения для этих restricted scope.
- **Microsoft Entra.** Зарегистрируйте приложение с поддержкой рабочих, учебных и личных аккаунтов Microsoft. Добавьте платформу **Web** и точный адрес возврата с фактическим портом API. В Microsoft Graph добавьте делегированное разрешение `Files.Read`; запрос MediaChips также включает `offline_access`. Создайте client secret и сохраните его **Value**.
- **Dropbox.** Создайте приложение типа **Scoped access** с **Full Dropbox**. Добавьте адрес в **Redirect URIs** и включите `files.metadata.read` и `files.content.read`. Для публичного распространения оформите Production status.

### Общий Google-клиент

Дополнительный аккаунт Google Drive, добавленный без Client ID, использует OAuth-клиент основного Google Drive вместе с его адресом возврата (`/api/drive/oauth/callback`; схема `CloudAccountInputSchema` его допускает). Права при этом остаются разными: основной Drive — `drive`, дополнительные — `drive.readonly`.

Общий клиент доступен, когда у основного Drive заданы Client ID и secret, он не в режиме mock, а его адрес возврата ведёт на текущий API. `GET /api/cloud-accounts/configuration` возвращает `googleClient: true`. Иначе создание аккаунта без ключей отвечает `google_client_missing` (409): сначала настройте основной Google Drive либо введите ключи для аккаунта.

### Адрес возврата из `.env`

`GOOGLE_OAUTH_REDIRECT_URI` с loopback-адресом и портом, не совпадающим с портом API (например, остаток от старого dev-сервера), игнорируется. Берётся автоматический адрес `http://127.0.0.1:<порт API>/api/drive/oauth/callback`; Desktop-клиенты Google принимают любой loopback-порт. Адрес, сохранённый в настройках подключения, имеет приоритет над `.env` и проверяется на порт при сохранении.

### Ключи на сервере (быстрое подключение)

Чтобы провайдер появился в быстром подключении, задайте переменные процессу API и перезапустите его. Нужны ключи провайдера и адрес возврата, который ведёт на этот API (не-loopback либо loopback с портом API).

```dotenv
MEDIA_CHIPS_CLOUD_REDIRECT_URI=https://mediachips.example/api/cloud-accounts/oauth/callback
MEDIA_CHIPS_CLOUD_GOOGLE_CLIENT_ID=
MEDIA_CHIPS_CLOUD_GOOGLE_CLIENT_SECRET=
MEDIA_CHIPS_CLOUD_ONEDRIVE_CLIENT_ID=
MEDIA_CHIPS_CLOUD_ONEDRIVE_CLIENT_SECRET=
MEDIA_CHIPS_CLOUD_DROPBOX_CLIENT_ID=
MEDIA_CHIPS_CLOUD_DROPBOX_CLIENT_SECRET=
```

Храните секреты в окружении сервера и не включайте их в распространяемую сборку. Без этих переменных (и без общего клиента) вводите ключи вручную в дополнительных настройках диалога.

## Пользовательский сценарий

1. В подключениях выберите существующий Google Drive либо добавьте облачный аккаунт. При серверной регистрации выберите провайдера и нажмите «Подключить»; иначе откройте дополнительные настройки и введите свой Client ID и secret (для Google без ключей используется общий клиент).
2. Сервер отвечает на `oauth/start` ссылкой согласия и режимом входа `mode`:
   - **`callback`** — браузер, в котором идёт вход, может открыть адрес возврата. Это любой публичный адрес, а для loopback — запрос с той же машины, где работает API (и сокет, и `X-Forwarded-For` — loopback). В браузере открывается всплывающее окно, в Electron — системный браузер.
   - **`paste`** — браузер не достаёт до loopback API: NAS, Docker bridge, LAN, обратный прокси. Публичный адрес для этого не нужен.
3. Режим `callback`: завершите согласие; страница результата сама закроется, интерфейс опросит статус и обновит список аккаунтов. Нажимать «Обновить» не нужно.
4. Режим `paste`: после согласия провайдер перенаправит на `http://127.0.0.1:<порт>/...`, и браузер покажет страницу «Не удаётся открыть сайт» — это ожидаемо. Скопируйте полный адрес из адресной строки (с `state=` и `code=`) и вставьте его в поле под подсказкой. Полная ссылка отправляется автоматически; кнопка «Готово» нужна при ручном вводе. Ссылка с чужим или просроченным `state` отклоняется с понятным сообщением.
5. `state` одноразовый, 64 hex-символа, действует 10 минут. Диспетчер по `state` находит владельца попытки среди всех провайдеров, поэтому вход можно завершить через любой из двух callback-маршрутов. PKCE S256 применяется в обоих Google-потоках.
6. «Отменить вход» инвалидирует попытку, включая уже запущенный обмен кода: поздний callback авторизацию не восстановит. Повторный вход отменяет предыдущую попытку только этого аккаунта. Отключение удаляет локальные токены, но не отзывает разрешение у провайдера.
7. Завершённая авторизация сохраняется после перезапуска API. Незавершённый вход после перезапуска считается истёкшим, начните заново.
8. При запросе файлов просроченный токен обновляется в API; параллельные запросы одного поколения авторизации делят один refresh. Ответ refresh без нового `refresh_token` сохраняет прежний. При `invalid_grant` токены удаляются и нужен повторный вход. Сбой сети действующую авторизацию не удаляет.

**Не входит в 2.0.0.** Electron и `npm run server` используют разные каталоги данных (userData и серверный каталог), поэтому подключения у них раздельные. Чтобы разделить их, задайте общий `MEDIA_CHIPS_DATA_DIR` либо открывайте backend Electron из браузера. Device flow Google не подходит: он не выдаёт полный scope `drive`.

## Совместимость Google Drive

| Подключение | Callback | Права | Идентичность файлов |
| --- | --- | --- | --- |
| Старое Google Drive | `/api/drive/oauth/callback` | `drive` для операций с оригиналами; старые read-only токены продолжают чтение | `gdrive://fileId` |
| cloudAccounts Google Drive | `/api/cloud-accounts/oauth/callback` | `drive.readonly` | `gdrive://accountUUID/encodedKey` |

Это независимые подключения с разными полномочиями и идентичностями. Нельзя автоматически переносить токены или подменять старое подключение новым: сломаются ссылки/права. Настройка, повторный вход и отключение сохраняют исходные идентификаторы подключений и карточек. Новая форма объясняет read-only характер дополнительного Google аккаунта. PKCE и правила callback согласованы, разница scope сохранена намеренно.

## Хранение и сборка

cloudAccounts уже использует host-local AES-256-GCM vault; старый Drive переведён на тот же механизм. Запись шифротекста атомарная, файлы создаются с 0600, каталог с 0700. Старый приватный JSON переносится при чтении; удаляется после успешной записи. Master key лежит на том же компьютере: это защита от случайного попадания в библиотеку/бэкап, не защита от пользователя, полностью контролирующего хост.

Найден и удалён игнорируемый git файл `public/drive-oauth-tokens.json`, а также его копия в `dist`. Добавлен запрет запуска Vite и сборки при повторном появлении этого файла. Не переносить эти токены в новый vault: их нужно отозвать. Старые артефакты и PWA caches могли уже содержать их; удаление из текущего дерева не отзывает выданный Google доступ.

## Проверки и реальная приёмка

Автоматические unit/component проверки используют подменённый token endpoint: они проверяют логику приложения, а не реальный OAuth. Проверяются одноразовый state, denial, отмена до/во время обмена, restart, logout race, PKCE, invalid_grant, параллельный refresh и перенос/очистка токенов. Пройдено 84 целевых теста (8 файлов), frontend/backend typecheck и production build.

HTTP acceptance suite использует настоящий локальный HTTP listener, но подменённого провайдера. В данной среде listener запрещён (`listen` возвращает `EPERM`); эти проверки не засчитываются как пройденные. В тестовых fixture callback исправлен на фактический API origin. E2E установленной Electron-сборки и настоящий provider OAuth не выполнены.

На машине с разрешёнными loopback-портами выполнить:

- `npm exec vitest run api/services/cloudAccounts/acceptance.test.ts`.
- Установить packaged app на чистый профиль, запустить рядом dev-сервер Vite, сверить callback в обоих подключениях и URL согласия. Проверить также занятый порт: не должно быть тихого перехода на dev callback.
- Серверный поток проверить в трёх окружениях: Electron (`callback`, системный браузер), `npm run server` с браузером на той же машине (`callback`, всплывающее окно) и Docker/NAS с браузером на другом устройстве (`paste`: поле вставки, автоотправка полной ссылки, ошибка при чужом `state`). Для каждого — основной Drive, дополнительный Google-аккаунт без своего Client ID, отмена, повторный вход, перезапуск и истёкший `state`.
- Для каждого провайдера: успешное согласие → автоматический статус → список реальных файлов → перезапуск приложения → список файлов → реальное обновление истёкшего access token.
- Отказ провайдера, закрытие браузера с последующей явной отменой, повторный вход другим аккаунтом, отмена во время callback, повтор старого callback, перезапуск при незавершённом входе, потеря сети и её восстановление.
- Отозвать доступ в настройках аккаунта провайдера, дождаться refresh: UI должен потребовать повторный вход; карточки и их идентификаторы сохраняются.
- Проверить отсутствие токенов/секретов в dist, asar, devtools responses и логах. Проверить обновление существующей установки с приватным legacy tokens.json.

### Результат ручной приёмки, 18 ноября 2026

Проверялось на macOS, провайдер Google Drive, собственный OAuth-клиент (для Electron — тип Desktop app).

| Окружение | Результат |
| --- | --- |
| `npm run server` + браузер на той же машине | Пройдено: основной Google Drive — вход, статус обновился сам, список реальных файлов, подключение сохранилось после перезапуска сервера. |
| Установленное приложение (Electron, `npm run pack`) | Пройдено частично: вход в облачный аккаунт Google Drive и в основной Google Drive, список реальных файлов, подключение сохраняется при повторном открытии диалога. Отдельно не фиксировалось: что вход шёл через системный браузер, автозакрытие страницы результата, полный перезапуск приложения. |
| Docker/NAS (режим `paste`) | **Не проверено вживую.** Режим вставки ссылки, автоотправка и ошибка при чужом `state` покрыты только автотестами; на реальном провайдере не выполнялись (решение от 18 ноября: пропустить для 2.0.0). |

Не выполнялось вручную (покрыто автотестами, на реальном провайдере не проверено): отмена входа и поздний callback, отзыв доступа у провайдера с повторным входом, дополнительный Google-аккаунт без своего Client ID (общий клиент основного Drive), истёкший `state`, реальное обновление истёкшего access token, перенос приватного legacy `tokens.json`, занятый порт 12321. OneDrive и Dropbox не проверялись (beta).

Поиск токенов и секретов в сборке (`app.asar` для `release/mac` и `release/mac-arm64`, `app.asar.unpacked`, `dist/`, `public/`; шаблоны `GOCSPX-…`, `ya29.…`, `1//0…`, `refresh_token`, `access_token`, `client_secret` со значением): совпадений нет, файла `drive-oauth-tokens.json` нет. Сборки сделаны 18 ноября до последних коммитов; на финальных установщиках проверку повторить.

## Точные внешние действия / блокеры

**Решение от 18 ноября 2026 (релиз 2.0.0):** MediaChips не поставляет собственный OAuth-клиент ни для Google, ни для Microsoft, ни для Dropbox. Каждый пользователь создаёт свой клиент у провайдера (README, `DOCKER.md`, справка «Cloud and NAS»). Поэтому пункты 2–4 и 6 ниже **не блокируют 2.0.0**: проверка приложения в Google, регистрация в Microsoft Entra и publisher flow нужны только для будущего входа «без собственных ключей». Пункт 1 выполнен 16 ноября.

1. Немедленно отозвать Google grant, которому принадлежали токены из public/dist, через настройки доступа Google Account. Очистить ранее собранные/разданные артефакты и их caches; при подозрении на утечку client secret перевыпустить его в Cloud Console. Не использовать найденные токены для приёмки.
2. Google Cloud Console: выбрать проект MediaChips, включить Drive API, оформить OAuth consent/branding, support contact, privacy policy, verified domains и аудиторию. Определить production OAuth client type и flow. Зарегистрировать оба точных callback для ручного Web client. Для отдельного Desktop flow использовать Desktop client и проверить требования обмена на реальных credentials. Секрет хранить только на стороне владельца API/управляемого broker, не распространять в сборке.
3. Согласовать необходимые Drive scopes: legacy `drive` и новые `drive.readonly`; пройти требуемую Google проверку этих scopes и выяснить применимость security assessment к выбранной инфраструктуре. Перевести consent из Testing в Production после одобрения; тестовые пользователи не подтверждают массовую доступность.
4. Microsoft Entra: зарегистрировать приложение с нужной аудиторией аккаунтов, `Files.Read` и `offline_access`, точным redirect и допустимым типом платформы; разрешить public-client PKCE flow, если он выбран, без confidential secret в клиенте. Dropbox App Console: зарегистрировать app, доступ к нужным файлам, `files.metadata.read`, `files.content.read`, точный redirect и offline access; получить production approval при необходимости.
5. Предоставить реальные client registrations/тестовые аккаунты и выполнить вышеуказанную приёмку на Windows/macOS/Linux. Успешный invalid-refresh-token preflight старого Drive подтверждает лишь ответ token endpoint, а не валидность redirect, scope, consent или реальный вход.
6. Для обещания «просто войти без собственных ключей» реализовать и проверить publisher flow после выбора реальной регистрации и инфраструктуры. Текущую ручную форму нельзя выдавать за завершённый массовый пользовательский сценарий.

Официальные источники: [Google Desktop OAuth/PKCE](https://developers.google.com/identity/protocols/oauth2/native-app), [Google Web server OAuth](https://developers.google.com/identity/protocols/oauth2/web-server), [Drive scopes](https://developers.google.com/workspace/drive/api/guides/api-specific-auth).
